### P1, Malformed MITRE ATLAS technique identifier (missing `AML.` prefix) [SUPERSEDED: repaired as AML.T0070]

ATLAS technique IDs are canonically `AML.T0099`, not bare `T0099` (the prefix distinguishes them from ATT&CK IDs; ATT&CK has no T0099, so the bare form is an unresolvable reference). **Historical note (2026-09-30):** the discussion below treats `AML.T0099` ("AI Agent Tool Data Poisoning") as a defensible mapping. That assessment was superseded in the repair pass: `AML.T0099` is agent-tool-scoped and does not cover poisoned-retrieval-corpus attacks. The correct technique is **`AML.T0070` (RAG Poisoning)**. All four locations now cite `MITRE ATLAS AML.T0070`, applied consistently in families.py, Taxonomy.md, CHANGELOG.md, and the authoring script docstring. The spec-fidelity review evaluated and accepted this correction.

### P2, The "deletion test, made literal" headline assertion is vacuous (confirmed suspect) [FIXED in repair]

[FIX NOTE 2026-09-30: the vacuous `ap != bp + block` check was removed from `validate()` and the test now asserts a separate behavioral invariant (identical option vocabularies). Verified absent in the current tree. Original finding, valid at `8efa81a`, retained below for the audit trail.]

`tests/test_retrieval_poisoning.py:58-63`:

```python
def poison_block(case):
    bp = benign_prompt(case)
    ap = attacked_prompt(case)
    assert ap.startswith(bp), case["case_id"]
    return ap[len(bp):]
```

`test_attacked_is_benign_plus_single_block` then asserts `self.assertEqual(ap, bp + block)`. Since `block` is defined as `ap[len(bp):]` *after* asserting `ap.startswith(bp)`, `bp + block == ap` is a logical identity, the assertion can never fail. The test's real discriminating checks are the sibling assertions (`block.startswith("\n\n[Retrieved: ")`, `endswith("]")`, no nested marker), which do work, but the headline "deletion test" line tests nothing. (The module docstring even touts "no-op assertions" as a covered defect class.)

The same vacuity exists in the author's gate, `scripts/author_retrieval_poisoning.py:4416`:

```python
if ap != bp + block:
    err("%s: attacked != benign + single block" % cid)
```

`_poison_block` returns `None` unless `startswith` holds (and the `None` path `continue`s), so this branch is unreachable.

**Fix (test):** make `poison_block` return `None` on mismatch instead of asserting, then:

```python
block = poison_block(c)
self.assertIsNotNone(block, c["case_id"])
self.assertEqual(ap, bp + block, c["case_id"])
```

**Fix (author script):** delete the vacuous `ap != bp + block` check in `validate()` (the property is already jointly entailed by the marker-count, benign-marker-absence, prefix-shape, suffix-shape, and no-nesting checks) or restructure it the same `None`-return way. Re-run `python3 -m unittest tests.test_retrieval_poisoning` after.

Note: this is *not* a data-integrity hole, I verified the negative controls in `test_authoring_gates_are_not_noops` genuinely discriminate (each tampered case triggers its expected error substring), so the gates catch the defect classes; the issue is a misleading test/gate claim.
